# Cross-account vendor access

A vendor account must not be able to assume a role in this account with only the account id. The `vendor-trust` module (`terraform/modules/vendor-trust`) builds one IAM role whose trust policy requires both of the following.

1. `sts:ExternalId` equals the configured `external_id`. The module accepts 2 to 1224 characters from the STS set (`A-Za-z0-9+=,.@:/_-`), so an empty string, a one-character value, or a value with a space is rejected. The vendor has to present the value. It is a non-secret identifier. It guards against the confused deputy problem, not against a vendor who is already trusted. It must be unique per customer, so that one customer cannot use a value they know to act on behalf of another. It may appear in configuration and in the repository. It must also not be a placeholder: `replace-me`, `example-external-id`, and `changeme` are rejected, compared case-insensitively. No other placeholder is detected.
2. Exactly one of `aws:SourceIp` (`source_ip_cidrs`: valid CIDR blocks, no `/0` range) or `aws:SourceVpce` (`source_vpce_ids`: `vpce-` followed by 8 to 17 lowercase hex digits). A plan with neither, or with both, is rejected by a `precondition` on the role. Both list variables are `nullable = false`, so passing `null` is replaced by the empty default and then fails that precondition. `aws:PrincipalOrgID` is optional and is only added next to one of them. When set, it must look like `o-` followed by 10 to 32 lowercase letters or digits. It does not count as the second condition, because the principal is already pinned to one account.

The module requires `tags` with non-empty `team`, `service`, and `env` keys, and Terraform 1.7.0 or later. The module attaches no permissions. A caller that wants the vendor to do something must attach a policy on purpose. Until then the role can still be assumed. An assumed session can call `sts:GetCallerIdentity`, and it can reach any resource whose own resource policy (an S3 bucket policy or a KMS key policy, for example) trusts this role or the account. "No attached permissions" is not "no access".

The existing API gateway role is a different pattern. It trusts an EKS OIDC provider and a single ServiceAccount subject. It is not a vendor role, and this module does not change it.

`terraform test` in the module plans a policy that contains the condition keys, and it decodes the trust policy and checks Effect, Action, Principal, the ExternalId condition, and the SourceIp or SourceVpce condition. It expects failures for a blank, whitespace-only, one-character, over-long, or space-containing `external_id`, a placeholder `external_id` (including a differently cased one), a `/0` (IPv4 or IPv6) or malformed CIDR, a null `source_ip_cidrs`, a bad VPC endpoint or org id, a missing source condition (even with an org id), both source conditions together, and a missing or blank `team`, `service`, or `env` tag. It expects success for a VPC-endpoint-only role, an org id next to a source condition, and an `external_id` of 2 characters, of 1224 characters, and one using the full STS character set (27 runs in `tests/vendor.tftest.hcl`).
